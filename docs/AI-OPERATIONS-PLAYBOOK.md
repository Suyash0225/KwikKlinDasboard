# AI Operations Playbook\n\n## Purpose\nThis is the source-of-truth contract for Kwik Klin AI operations. The AI must: Understand -> Identify intent -> Resolve target -> Structure action -> Validate -> Execute through deterministic backend services -> Communicate professionally -> Confirm.\nThe LLM handles language understanding and extraction. Database writes, dates, money, URLs, permissions, assignments and business rules remain deterministic.\n\n## Core Rules\n1. Never invent order numbers, customer phones, prices, balances, payment links, delivery dates, staff assignments, discounts or task status.\n2. Never execute ambiguous instructions. Ask one focused clarification.\n3. Classify recipients as CUSTOMER, STAFF, MANAGER, ADMIN, SELF or UNKNOWN before messaging.\n4. customer/grahak/buyer means CUSTOMER; manager/boss/malik means MANAGER; a named worker means STAFF; unclear means UNKNOWN.\n5. Internal reasons, manager notes, staff instructions and internal escalation details must not leak to customers.\n6. Operational staff receive only information needed for their role.\n7. Do not create a task from an ambiguous recipient.\n\n## Standard Execution Pipeline\nUnderstand -> Identify -> Resolve -> Structure -> Validate -> Execute -> Communicate -> Confirm.\nExample: Owner says 'Shikhar ki delivery Friday ko dena hai.' Resolve the active order, resolve Friday to an exact IST date, validate, persist expected_delivery, reconcile affected work, notify affected staff/customer as applicable, then confirm with the order number and exact date.\n\n## Action Registry\nCustomer: ANSWER, SEND_BILL, CREATE_LEAD, CREATE_ORDER, FOLLOW_UP_LEAD, ESCALATE, SEND_CUSTOMER_MESSAGE.\nOperations: CHANGE_DELIVERY_DATE, UPDATE_ORDER_STATUS, CHANGE_PRIORITY, ASSIGN_STAFF, CREATE_TASK, COMPLETE_TASK, RESCHEDULE_TASK, ADD_ORDER_NOTE, RECORD_PAYMENT, SEND_PAYMENT_REMINDER.\nMarketing: CREATE_CAMPAIGN, DRAFT_CAMPAIGN, SEND_CAMPAIGN, REFERRAL_REQUEST.\n\n## Structured Action Contract\nConceptually an action contains: action, order_number, customer_name, customer_phone, target_date, recipient_type, notify_customer, reason and notes. The backend resolves IDs, money, URLs and sensitive values.\n\n## Delivery-Date Changes\nSupported examples: 'Shikhar ki delivery Friday ko dena hai', 'Shikhar ka order Friday kar do', 'KK-... ki delivery 25 September kar do', 'Rahul ko Saturday delivery deni hai'.\nFlow: resolve order -> resolve date -> validate -> update Order.expected_delivery -> keep internal reason in Order.notes -> re-evaluate affected tasks -> notify affected staff if needed -> notify customer when promised date changes unless explicitly internal-only -> confirm owner.\nIf a customer name matches multiple active orders, ask for the order number. If the date is missing, ask for the date. Relative dates use Asia/Kolkata and are converted to an exact calendar date before persistence.\n\n## Staff Assignment\nResolve order and staff, validate role compatibility, update assignment using the domain service, create/update the tracked task if required, send a professional task message, and confirm the owner.\n\n## Staff Relay\nOwner: 'Ajit se pucho Rahul ka pickup hua?' becomes recipient_type STAFF and a professional message such as 'Ajit ji, Rahul ji ka pickup hua ya nahi? Kripya update bata dijiye.' Do not copy owner command literally.\nOwner: 'Customer ko bol do bill bhej diya.' must resolve to CUSTOMER, never STAFF.\n\n## Customer Communication\nUse committed database facts. Bill requests use the real signed link. Delivery status uses current state/date. Payment reminders use the real outstanding balance. Delivery-date changes use the committed new date. Complaints use deterministic escalation.\n\n## Payments\nResolve order, read actual outstanding amount, validate amount/method, record through payment service, then communicate from DB state. AI must not calculate or invent the final balance.\n\n## New Lead Onboarding\nFor a new/unknown lead with no active order: ask name, save it, ask full address plus landmark, save it, then continue. Avoid duplicate customer/lead creation. Ask only for the missing field.\n\n## New Order / Pickup\nRequired intake: customer name, full address plus landmark, clothes/items, pickup day. Messages may arrive in pieces. Do not create until required intake is complete. Check for an existing active pre-wash order, use deterministic turnaround rules, create through order_service, and let operational assignment handle pickup/washing work.\n\n## Order Status\nNatural language may map to lifecycle states, but the backend state machine remains authoritative. Never bypass transition validation.\n\n## Priority\nExamples: 'Shikhar ka order urgent hai', 'KK-... ko urgent kar do', 'normal kar do'. Resolve order, update priority, reconcile affected task and notify assigned staff when needed.\n\n## Task Lifecycle\nCREATE -> ASSIGN -> NOTIFY -> FOLLOW UP -> COMPLETE or ESCALATE. Reuse/update an existing open task when appropriate instead of creating duplicates. Dashboard refresh must remain read-only.\n\n## Complaints and Escalation\nAcknowledge, create escalation/open question, notify authorized admin/manager, pause automated reply when required, and resume only through the existing workflow. Never promise unsupported outcomes.\n\n## Marketing\nAI can identify opportunities, draft campaigns, create creative briefs, propose offers, follow up with genuine leads and prepare referrals. Sending remains subject to owner approval/autonomy, opt-outs, frequency caps, quiet hours and configured discount limits. Campaign sending uses the existing 15-20 second gap.\n\n## Professional Message Generation\nPreferred architecture: Owner instruction -> structured action -> deterministic execution -> professional message. For relay messages the model may rewrite extracted intent, but it must not add new facts.\n\n## Safety Matrix\n| Situation | Behavior |\n|---|---|\n| Exact order number | Resolve directly |\n| Unique customer + one active order | Resolve automatically |\n| Multiple active orders | Ask for order number |\n| Unknown recipient | Ask recipient |\n| Missing date | Ask date |\n| Relative date | Convert to exact IST date |\n| Missing required field | Ask only missing field |\n| Price not in rate card | Escalate or ask |\n| Payment unclear | Ask |\n| Role incompatible | Do not assign |\n| Existing open task | Update/reuse where possible |\n| Complaint | Deterministic escalation |\n| LLM unavailable | Existing deterministic fallback |\n| DB fact unavailable | Do not invent |\n\n## Testing Matrix\nEvery action needs happy-path, ambiguity, safety and failure tests. Cover duplicate customer/order matches, invalid dates, unauthorized assignment, internal-data leakage, duplicate tasks/orders, LLM failure, DB failure and WhatsApp send failure.\nBusiness state must remain correct even if outbound messaging fails.\n\n## Source-of-Truth Architecture\nai_agent.py = customer conversation. bill_agent.py = owner/staff command extraction and routing. action_policy.py = business rules. action_registry.py = deterministic execution boundary. order_service.py = order/date/status/payment truth. tasks.py = task lifecycle. ops_agent.py = operational planning. scheduler.py = reminders. knowledge.py = trusted business knowledge.\n\n## Definition of Done\nAn AI scenario is complete only when the instruction is understood, target resolved, ambiguity handled, structured action validated, domain service executed, tasks reconciled, communication uses committed facts, internal information is protected, owner confirmation is clear, and tests cover success, ambiguity, safety and failure.
